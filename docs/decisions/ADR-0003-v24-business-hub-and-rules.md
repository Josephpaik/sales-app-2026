# ADR 0003: V2.4 수정안 반영 — 사업관리 허브 통합과 서버 측 업무 규칙의 프로토타입 선반영

## 1. 상태 (Status)
- 현재 상태: 수락됨(Accepted) — 프로토타입 v1.1
- 결정 날짜: 2026-10-12
- 승인자: CISO 백원광

## 2. 배경 (Context)
- 영업지원부서가 전달한 수정안 V2.4(2026-09-29)는 49개 레이어로 누적된 시뮬레이션이며, 대시보드·영업현황·제품라인 입력·사업관리 통합·매출채권·내부보고·발급/출고 이력을 요구한다.
- 레이어가 누적되면서 메뉴 이동 시 화면 구조가 달라지고 중복 탭이 생기는 문제가 있었다(V24·V25·V33에서 자체 정리).
- 매출채권·발급·출고·내부보고는 수행계획서 v1.1 §2-2의 "검토/후속" 영역이어서 1차 범위 판정이 아직 남아 있다.

## 3. 결정 (Decision)
- 메뉴는 WORKSPACE(대시보드·영업 현황·사업관리) / 기준정보 / 관리자 3구역으로 고정하고, 계약·직출·발급·출고·채권·보고·문서함은 **사업관리 허브 한 곳의 동일 탭 체계**(`BizLayout`)로만 노출한다. 프로젝트 세부내용 탭도 6개로 고정한다.
- 업무 규칙(서티 승인 전 수주 차단, 본사업 필수, 검수완료 선행, 발급·출고 수량 검사, 매출채권 상태 계산, 거래처 등재 승인 전 계약 저장 불가, 문서번호 채번)은 UI가 아니라 `src/api/index.ts`에 둔다. 실제 구현에서 이 함수들은 Django 서비스 계층으로 1:1 이관한다.
- 제품 마스터는 TQS 제품군×버전 대신 영업지원부서 엑셀 '제품분류' 216 품목을 기준으로 한다(V2.4 결정 승계). 설계 단계 코드 정의서에서 TQS 제품코드와의 매핑을 확정한다.
- V2.4의 매입발주서 PDF 생성·3단계 결재·내부통제 케이스 화면은 반영하지 않는다(서버 구현 영역이거나 1차 범위 밖).

## 4. 결과 (Consequences)
- 긍정적 효과: 메뉴·탭 체계가 단일화되어 현업 리뷰에서 "같은 화면이 다르게 보이는" 혼란이 사라진다. 매출채권·발급·출고 규칙을 실제 동작으로 검증할 수 있어 분석 단계 범위 판정 근거가 생긴다.
- 부정적 영향/비용: 화면 수가 18 → 25개로 늘어 설계 단계 화면 정의서 작업량이 증가한다. 매출채권·내부보고가 1차에 포함되면 구축 S4~S5 범위가 커지므로 절단 규칙(§2-2) 합의가 선행되어야 한다. 시드 데이터 스키마 변경으로 v1.0 브라우저 저장 데이터는 폐기된다.
